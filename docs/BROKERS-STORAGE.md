# Протокол проверки брокеров сообщений и распределенных хранилищ

Домашнее задание: подключить Kafka, RabbitMQ и NATS, погонять их под
нагрузкой с отказом узлов; подключить S3, HDFS и Cassandra и проверить так
же; настроить сбор и поиск в Elasticsearch. Звездочки: NATS, запросы к
Cassandra, теги и версии в S3.

## Что построено

Событие идет через всю систему. `POST /messages` сохраняет сообщение в
PostgreSQL и публикует событие во все настроенные брокеры. Воркер
`cmd/consumer` читает события из своего брокера и пишет их в Cassandra и
Elasticsearch. Файлы идут мимо брокеров: `POST /files` кладет объект в S3
или HDFS, метаданные с тегами дублируются в Elasticsearch.

```
                         ┌── Kafka ────┐
POST /messages ─ app ────┼── RabbitMQ ─┼── consumer ──┬── Cassandra   GET /events
                         └── NATS ─────┘              └── Elasticsearch  GET /search
POST /files ──── app ────┬── S3 (MinIO)  ── теги, версии, Range, multipart
                         └── HDFS        ── блоки по датанодам
```

Все интеграции включаются переменными окружения. Без них приложение работает
как раньше, боевой стенд не тронут.

Стендов два, поднимаются по очереди - вместе не влезают в память:

| Стенд | Файл | Состав |
|---|---|---|
| Брокеры | `ds/docker-compose.brokers.yml` | Kafka, RabbitMQ и NATS по 3 узла, Elasticsearch, PostgreSQL, app, 3 воркера - 15 контейнеров |
| Хранилища | `ds/docker-compose.storage.yml` | MinIO 4 узла, HDFS (namenode + 3 датаноды), Cassandra и Elasticsearch по 3 узла, Kafka, PostgreSQL, app, воркер - 18 контейнеров |

```bash
make brokers-up && make brokers-test && make brokers-down
make storage-up && make storage-test && make s3-test && make cassandra-test && make search-bench
```

Стенду хранилищ нужно около 10 ГиБ памяти для Docker. На 8 ГиБ узлы
Cassandra убивает OOM-killer.

## 1. Как настроены брокеры

| | Kafka | RabbitMQ | NATS JetStream |
|---|---|---|---|
| Репликация | топик RF=3, `min.insync.replicas=2` | quorum-очередь на 3 узлах | поток `R=3`, файловое хранилище |
| Подтверждение записи | `acks=all` | publisher confirms | ack от лидера потока |
| Раздача работы | consumer group, 6 партиций | конкурирующие консьюмеры, prefetch 32 | durable pull-консьюмер |
| Подтверждение обработки | ручной коммит offset | `ack` / `nack` с возвратом | `ack` / `nak` |

Везде одно правило: пока большинство реплик не подтвердило, запись не
принята. Сообщение не подтверждается, пока воркер не разложил его по
хранилищам. Повторная доставка не страшна: в Cassandra ключ - id события, в
Elasticsearch документ пишется под тем же id.

Публикация параллельная и best-effort. Недоступный брокер не валит запрос,
но виден в метрике `otus_broker_published_total{result="error"}`.

## 2. Брокеры под нагрузкой

k6 держит 150 запросов в секунду на `POST /messages`. Каждый запрос дает три
публикации.

```
задержка POST /messages: avg=17.98ms med=14.13ms p(90)=20.83ms p(95)=27.87ms
```

Метрики приложения и воркеров за прогон в 4501 сообщение:

| Брокер | Публикация, среднее | Доставка до обработки |
|---|---|---|
| NATS JetStream | 0.65 мс | 103 мс |
| RabbitMQ | 8.38 мс | 117 мс |
| Kafka | 12.00 мс | 1833 мс |

NATS быстрее на порядок: лидер потока подтверждает из памяти. Kafka ждет
флаш на диск у всех синхронных реплик, RabbitMQ - коммита в raft. Полторы
секунды доставки у Kafka - это не брокер, а воркер, разбор ниже.

## 3. Отказы узлов брокеров

`scripts/broker-failover-test.sh` держит нагрузку, находит узел-лидер, гасит
его на 20 секунд, возвращает и считает доехавшие события. Считаем от общего
числа запросов, а не от ответов 201: запрос с таймаутом у клиента все равно
сохранил сообщение и опубликовал событие.

| Сценарий | Запросов | Kafka | RabbitMQ | NATS |
|---|---|---|---|---|
| Базовый прогон | 4500 | 4500 | 4500 | 4500 |
| Отказ узла Kafka с лидерами партиций | 6578 | 6576 (-2) | 6578 | 6578 |
| Отказ узла RabbitMQ с лидером очереди | 6751 | 6751 | 6751 | 6751 |
| Отказ узла NATS с лидером потока | 6751 | 6751 | 6751 | 6748 (-3) |
| Потеря кворума Kafka (2 узла из 3) | 2638 | 2508 (-130) | 2638 | 2638 |

Отказ одного узла нигде не дал ни одной ошибки HTTP: клиенты сами нашли
новых лидеров. Потери в единицы событий - это публикации, попавшие в момент
переключения и исчерпавшие повторы.

Kafka переизбирает лидеров и сжимает список синхронных реплик:

```
до отказа:       Partition: 0  Leader: 1  Replicas: 1,2,3  Isr: 1,3,2
kafka-3 погашен: Partition: 0  Leader: 1  Replicas: 1,2,3  Isr: 1,2
после возврата:  Partition: 0  Leader: 1  Replicas: 1,2,3  Isr: 1,2,3
```

RabbitMQ держит очередь на трех узлах, лидер переезжает сам:

```
name            type    leader          members
otus.messages   quorum  rabbit@rabbit-2 [rabbit@rabbit-1, rabbit@rabbit-2, rabbit@rabbit-3]
```

NATS показывает поток и реплики (вывод с узла-лидера):

```
поток OTUS | сообщений: 38672
лидер: nats-3 | реплики: [('nats-1', в строю), ('nats-2', в строю)]
```

### Потеря кворума Kafka

Два узла из трех погашены, `min.insync.replicas=2` не выполняется:

```
Kafka write errors: [19] Not Enough Replicas: the number of in-sync replicas
is lower than the configured minimum and requiredAcks is -1
```

Kafka потеряла 130 событий из 2638 - 5%. RabbitMQ и NATS не потеряли ничего,
их кластеры были целы.

1188 запросов клиент счел неуспешными: публикация синхронная, ожидание Kafka
держало ответ до таймаута. Тот же урок, что был с etcd - таймаут у клиента не
значит, что операция не выполнена. Сообщения сохранились и разошлись.

Синхронная веерная публикация привязывает время ответа к самому медленному
брокеру. Лечится паттерном outbox: писать событие в ту же транзакцию, что и
сообщение, а отправлять отдельным процессом.

### Дефект, который вылез в этом тесте

Первый прогон потерял 891 событие, все с одной ошибкой:

```
"msg":"не удалось опубликовать событие","broker":"kafka","err":"context canceled"
```

Публикация шла с контекстом HTTP-запроса. Клиент отваливался по таймауту, Go
отменял контекст, отправка уже сохраненного сообщения обрывалась. Исправлено
через `context.WithoutCancel` со своим сроком. После этого в тех же условиях
потерялось 130 событий вместо 891, и все - настоящие отказы Kafka.

## 4. Масштабирование обработки

Гасим воркеры, копим очередь нагрузкой, поднимаем обратно и меряем время
разбора.

| Режим | Накоплено | Разобрано | Скорость |
|---|---|---|---|
| 1 воркер, коммит offset на каждое событие | 4000 | 20.3 с | 196 событий/с |
| 1 воркер, коммит пачкой раз в секунду | 4000 | 18.6 с | 214 событий/с |
| 3 воркера, коммит пачкой | 4001 | 10.3 с | 386 событий/с |

Пакетный коммит дал 9%, значит дело не в нем. Потолок одного воркера в 200
событий в секунду задает синхронный поход в Elasticsearch на каждое событие:
5 мс на запрос, по одному запросу за раз. Отсюда и задержка доставки в 1.8
секунды у Kafka при 150 rps - воркер работает на пределе.

Три воркера дают двукратный рост вместо трехкратного: упирается уже сам
Elasticsearch. Правильнее не добавлять воркеров, а перейти на bulk.

## 5. Как настроены хранилища

| Система | Конфигурация | Роль |
|---|---|---|
| MinIO (S3) | 4 узла, erasure coding EC:2, версионирование включено | файлы: `POST /files`, `GET /files/{key}` с `Range`, теги, версии |
| HDFS | namenode + 3 датаноды, репликация 3, блок 16 МБ | те же маршруты с `?backend=hdfs` |
| Cassandra | 3 узла, RF=3, чтение и запись QUORUM | лента событий `GET /events`, выборка `GET /events/{id}` |
| Elasticsearch | 3 узла, 3 шарда с 1 репликой, русский анализатор | `GET /search`, поиск файлов по тегам |

Схема Cassandra сделана под запросы, а не под данные. Одна таблица с
партицией на сутки для ленты, вторая с id в ключе для точечной выборки. Обе
пишутся одним логированным батчем.

## 6. Отказы узлов хранилищ

`scripts/storage-failover-test.sh` держит 100 операций в секунду: 60 созданий
сообщений, 20 загрузок объектов, 20 чтений диапазона. Узлы гасятся по
очереди.

| Сценарий | Операций | Неуспешных | p95 |
|---|---|---|---|
| Базовый прогон | 3002 | 0 | 15.9 мс |
| Отказ узла MinIO (1 из 4) | 4502 | 0 | 21.5 мс |
| Отказ датаноды HDFS (1 из 3) | 4502 | 0 | 38.3 мс |
| Отказ узла Cassandra (1 из 3) | 4503 | 0 | 24.2 мс |
| Отказ узла Elasticsearch (1 из 3) | 4503 | 0 | 22.5 мс |
| Отказ 2 узлов MinIO из 4 | 4503 | 417 | 92.5 мс |

Отказ одного узла не заметил никто. Отказ двух узлов MinIO разделил операции
по границе кворума:

```
✓ сообщение создано    100%
✓ кусок получен        100%
✗ объект загружен       53% — ✓ 484 / ✗ 417
```

Так и работает erasure coding: при `EC:2` на четырех дисках чтение
собирается из двух оставшихся, а записи нужен кворум.

Elasticsearch на отказ узла отвечает переходом в yellow. Копии шардов
теряются, primary остаются на живых узлах, поиск работает:

```
до отказа:      status green,  nodes 3, active_shards 8, unassigned 0
es-2 погашен:   status yellow, nodes 2, active_shards 6, unassigned 2
поиск при этом: GET /search?q=отчет -> 200 за 5 мс
```

Асинхронный путь брокер - воркер - хранилища отработал весь прогон без
ошибок, данные сошлись:

```
сообщений в PostgreSQL:      19741
событий в Cassandra:         19741
документов в Elasticsearch:  19741
ошибок воркера:              0
```

## 7. Elasticsearch: сбор и поиск

Воркер индексирует каждое событие под его id, приложение ищет через
`GET /search?q=...`. Индекс с русским анализатором: стоп-слова и стеммер.
Параметр `engine` выполняет тот же запрос в PostgreSQL (`ILIKE`) или в
Cassandra (перебор таблицы) - сравнение идет на одних данных.

102 344 сообщения, среднее по 5 прогонам:

| Запрос | Elasticsearch | PostgreSQL `ILIKE` | Cassandra (перебор) |
|---|---|---|---|
| отчет | 24 мс, 1950 совпадений | 25 мс, отдал 10 | 1296 мс, просмотрено 102 346 |
| квартальный | 6 мс, 644 | 28 мс, отдал 10 | 1211 мс |
| доставка | 6 мс, 1353 | 40 мс, нашел 0 | 1258 мс, нашел 0 |
| сообщение | 6 мс, 1371 | 28 мс, отдал 10 | 1208 мс |

На 26 тысячах строк было так: Elasticsearch 7-38 мс, PostgreSQL 0-13 мс,
Cassandra 343-476 мс. Данных стало в 3.8 раза больше. У PostgreSQL и
Cassandra время выросло втрое, у Elasticsearch не изменилось. Один читает
индекс, двое других читают все.

`ILIKE '%подстрока%'` не может использовать индекс, это видно в плане:

```
Limit  (cost=0.00..15.26 rows=10) (actual time=0.014..9.096 rows=10)
  ->  Seq Scan on messages  (actual time=0.010..9.090 rows=10)
        Filter: (text ~~* '%отчет%'::text)
        Rows Removed by Filter: 23741
```

Но скорость тут не главное. Полнотекстовый поиск отвечает на вопрос, на
который два других не отвечают вообще:

| Запрос | Elasticsearch | PostgreSQL `ILIKE` |
|---|---|---|
| сообщение | 1371 | 1 |
| сообщения | 1371 | 0 |
| сообщений | 1371 | 0 |

Стеммер приводит словоформы к одной основе, `LIKE` сравнивает подстроки. Для
русского текста это принципиально. Еще Elasticsearch отдает общее число
совпадений: PostgreSQL с `LIMIT` знает только первые десять, Cassandra не
знает вообще.

Альтернатива у PostgreSQL есть - `tsvector` с GIN-индексом тоже умеет
морфологию. Elasticsearch выбран за другое: поисковый индекс живет отдельно
от транзакционной базы, тяжелые запросы не мешают записи, индекс сам себя
реплицирует и масштабируется.

С файлами так же. В S3 нет поиска по тегам, их можно только прочитать у
известного объекта. Поэтому метаданные дублируются в индекс:

| Как найти файлы с тегом `kind=report` | Время |
|---|---|
| Индекс Elasticsearch | 47 мс |
| Перебор бакета: список плюс теги каждого объекта | 2032 мс |

На 2175 объектах разница в 43 раза, и она растет с размером бакета.

## 8. Звездочка: NATS

NATS проверен наравне с Kafka и RabbitMQ: публикация с подтверждением,
durable-консьюмер, отказ узла с лидером потока под нагрузкой. Цифры в
разделах 2 и 3.

Итог: самая быстрая публикация из трех (0.65 мс против 8.38 и 12.00), потеря
3 событий из 6751 при отказе лидера потока, самая простая настройка - три
флага вместо конфигов и служебных топиков. Минус: JetStream моложе, у него
нет ни коннекторов Kafka, ни средств управления RabbitMQ.

## 9. Звездочка: запросы к Cassandra

`scripts/cassandra-queries-test.sh`. Время меряет сама Cassandra через
`TRACING ON`. В таблице 23 345 строк.

| Запрос | Время | Что происходит |
|---|---|---|
| По ключу партиции (лента за сутки, LIMIT 5) | 3.1 мс | один узел, одна партиция |
| По первичному ключу `events_by_id` | 1.4 мс | точечное чтение |
| По неключевой колонке с `ALLOW FILTERING` | 1.5 мс | `LIMIT 5` останавливает перебор на первом диапазоне |
| То же по вторичному индексу | 2.7 мс | индекс сначала надо построить |
| `count(*)` по таблице | 509 мс | 49 диапазонов, обход всего кольца |

Запрос по неключевой колонке без `ALLOW FILTERING` просто запрещен:

```
InvalidRequest: Cannot execute this query as it might involve data filtering
and thus may have unpredictable performance
```

Чего в CQL нет совсем: `JOIN` (синтаксическая ошибка), `GROUP BY` по
неключевой колонке, `OR` в условии. Поэтому данные и лежат в двух таблицах.
Сначала запрос, потом таблица под него.

`INSERT` - это upsert, уникальности нет:

```
INSERT ... VALUES (-1, 'первая запись', ...);
INSERT ... VALUES (-1, 'вторая запись затерла первую', ...);
SELECT id, text FROM events_by_id WHERE id = -1;
 -1 | вторая запись затерла первую
```

Уникальность дает только легковесная транзакция, и платит за нее четырьмя
раундами Paxos:

```
INSERT ... IF NOT EXISTS;
 [applied] | id | text
     False | -1 | вторая запись затерла первую
```

На живом кластере работают все уровни консистентности. Гасим один узел из
трех:

```
UN  172.22.0.16   ...
UN  172.22.0.4    ...
DN  172.22.0.17   ...

CONSISTENCY ONE     -> строка прочитана
CONSISTENCY QUORUM  -> строка прочитана
CONSISTENCY ALL     -> Cannot achieve consistency level ALL
                       info={'required_replicas': 3, 'alive_replicas': 2}
```

Запись с `ALL` падает, с `QUORUM` проходит. Приложение работает на QUORUM,
поэтому отказ узла оно и не заметило.

Еще всплыло, что вторичный индекс строится не мгновенно: запрос по нему во
время сборки вернул `ReadFailure`.

Cassandra - не реляционная СУБД с другим синтаксисом. Стоимость запроса
известна заранее, если он идет по ключу, и не ограничена ничем, если не идет.
Лента событий и выборка по id ложатся на эту модель хорошо, полнотекстовый
поиск - нет.

## 10. Звездочка: работа с S3

`scripts/s3-features-test.sh`.

**Теги.** Ставятся при загрузке (`?tags=kind=report,owner=evgenza`), меняются
через `PUT /files/{key}/tags`. MinIO их видит:

```
Name    : http://localhost:9000/otus-files/отчет-квартал.txt
kind    : report
owner   : evgenza
quarter : q3
```

Поиск по тегам средствами S3 - это перебор бакета с запросом тегов на каждый
объект: 2032 мс против 47 мс по индексу.

**Версионирование.** Бакет создается с включенным версионированием.
Перезапись не затирает, а добавляет версию:

```
[14:30:11 UTC] 25B b68ac6f6-3651-496d-83d6-f47c6e18656a v3 PUT версии.txt
[14:30:11 UTC] 25B bfa14269-5980-435e-8ff8-e03cd32c8da9 v2 PUT версии.txt
[14:30:11 UTC] 25B 561ea678-bf4e-4145-949d-b59b43df93fd v1 PUT версии.txt

текущее содержимое:  третья версия
версия 561ea678-...: первая версия
```

**Частичная загрузка.** Заголовок `Range` уходит в хранилище, а не режется в
приложении:

```
$ curl -H 'Range: bytes=10-19' .../files/диапазон.txt
HTTP/1.1 206 Partial Content
Content-Length: 10
Content-Range: bytes 10-19/36
abcdefghij
```

**Огромный файл.** 200 МБ уходят multipart-загрузкой по 16 МБ. Клиент режет
поток сам, размер тела знать заранее не нужно. Число частей видно в ETag:

```
{"key":"big.bin","size":209715200,"etag":"e47471d333b9484e6593b27ae5fca5fc-13","parts":13}

скачивание целиком: 2.7 с, файл вернулся байт в байт
```

Чтобы прочитать мегабайт из середины, качать весь файл не нужно: диапазонное

**Тот же файл в HDFS.** Режется на 13 блоков по 16 МБ, каждый лежит на трех
датанодах:


## 11. Что починили по итогам

Нагрузка вскрыла четыре дефекта в коде:

1. **Публикация умирала вместе с запросом.** Контекст HTTP-запроса отменялся
   по таймауту клиента и обрывал отправку уже сохраненного сообщения - 891
   потерянное событие. Лечится `context.WithoutCancel` со своим сроком.
2. **Гонка при создании индекса Elasticsearch.** Приложение и воркер стартуют
   вместе, оба создают индекс. Проигравший получал
   `resource_already_exists_exception` и молча оставался без поиска. Теперь
   эта ошибка считается успехом.
3. **Файл в HDFS оставался незакрытым.** `Close` возвращает
   `replication in progress`, пока блоки не разошлись по датанодам. Без
   повторов запись падала. Добавлены повторы с растущей паузой, как в
   java-клиенте.
4. **`refresh` на каждую запись в Elasticsearch.** Стоит полтора раза по p95
   (24 мс против 16 мс) и не нужен: документ и так виден через секунду.
   Выключен по умолчанию, включается через `ELASTIC_REFRESH`.

Пятая правка - в стенде, а не в коде. Namenode переформатировал файловую систему
при каждом рестарте контейнера. Датаноды со старым cluster id отказывались
регистрироваться, и HDFS оставался без единой живой датаноды. Теперь формат
выполняется только при первом запуске.

## Оценка результатов

- Отказ узла в каждом из семи кластеров прошел под нагрузкой без ошибок HTTP
  и с потерями в единицы событий на десятки тысяч.
- Потеря кворума ломает только тот брокер, который его потерял. Разница между
  "узел упал" и "кворум потерян" важнее разницы между брокерами: первое
  проходит незаметно, второе требует деградации на стороне приложения.
- Узкое место обработки оказалось не в коммитах offset и не в брокере, а в
  синхронной индексации в Elasticsearch.
- Данные сошлись точно: 19 741 сообщение в PostgreSQL, столько же событий в
  Cassandra и документов в Elasticsearch.
- Elasticsearch выигрывает не скоростью. Его время не растет с объемом
  данных, и он ищет по словоформам.
